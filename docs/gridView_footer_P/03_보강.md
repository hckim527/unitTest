**구성 방식**

- `@dynamic N` 이므로 런타임 변경 없이 **렌더 시점 설정**으로만 검증. `con_class` selectbox(미설정 / `oddClass` / `oddClass evenClass`) 변경 후 `body_sample.xml` 기본 제공 `Target 재생성` 버튼(→ `comp_init`) 으로 반영.
- `cm/gcc/common.xml` 의 `createBasicGridView` 는 `<w2:footer>` 를 포함하지 않으므로 `comp_init` 에서 `<w2:footer>` 를 포함한 gridView XML 을 직접 구성해 `$p.dynamicCreate` 로 생성 (common.xml 무수정).
- class 검증용 CSS 는 프로젝트 공용 `css/tc.css:45-46` 의 `.oddClass` / `.evenClass` 사용.

**실측 raw 값 (con_class = "oddClass evenClass")**

- 선언 마크업 : `<w2:footer style="" id="footer1" class="oddClass evenClass"> ... </w2:footer>`
- 렌더된 Footer 영역 요소 outerHTML(앞부분) :
  `<table id="mf_target1_foot_table" class="gridFooterTableDefault" style="position: absolute; bottom: 0px; table-layout: fixed; border-collapse: collapse; border-spacing: 0px; width: 559px;">`
- `mf_target1_foot_table.className` = **`gridFooterTableDefault`** (설정한 `oddClass evenClass` **미적용**)
- Footer Column 영역 요소 : `td#mf_target1_footer_col1`, `className` = `gridFooterTDDefault gridFooterTDDefault_data  mf_target1_footer__column0  `
- con_class 미설정으로 재생성 시에도 동일하게 `gridFooterTableDefault`

→ **가이드(`@propval |`) 와 실측 일치.** 설정한 class 는 렌더 결과에 반영되지 않고 엔진 기본 클래스만 적용됨. (article/audio/video/canvas 의 `class` 와 정반대)

**원인 (엔진 소스 대조, 참고)**

- `uiplugin/gridView/layoutController.js:301` : `this.options.footerTableClass = this.struct.foot.attr["class"] || "gridFooterTableDefault";`
- 그러나 실측 `target1.struct.foot.attr` = `{"id":"footer1","className":"oddClass evenClass"}` — 파서가 `class` 를 **`className` 키로 정규화**해 저장하므로 `attr["class"]` 는 항상 `undefined` → 기본 클래스로 폴백.
- header/gBody 도 같은 코드 경로(`attr["class"]`)라 동일 구조로 보이며, 결과적으로 가이드가 규정한 "참고용" 동작과 일치하므로 **결함이 아니라 현행 스펙**으로 판단.

**@spec 근거 (Footer 영역 / Footer Column 영역 분리)**

- Footer 영역 = `table#mf_target1_foot_table` (footer 의 `class` 대상, 기본 클래스 `gridFooterTableDefault`)
- Footer Column 영역 = `td#mf_target1_footer_col1` (footer 의 `columnClass` 대상, 기본 클래스 `gridFooterTDDefault`)
- 두 영역이 별개 요소·별개 기본 클래스로 렌더됨을 출력해 "별도 정의"를 입증. columnClass 속성 자체의 동작은 검증하지 않음.

**가이드 대조 결론**

- (1) CSS 정의 클래스 적용 : `labelClass` 설정 시 일반 Footer Cell 의 computed `background-color = rgb(255,192,203)` → 일치.
- (3) 치환(추가 아님) : 설정 시 기본 클래스 `gridFooterTDDefault` 가 class 토큰에서 완전히 사라지고, 기본 클래스가 주던 테두리(1px solid 회색)까지 `0px none` 으로 사라짐 → 일치.
- (4) 미설정 시 `gridFooterTDDefault` → 일치.
- (5)(6)(7)(8) 파생 클래스 `_data` / `_rowNumber` / `_rowStatus` → 일치.
- (2) 공백 2개 클래스 **실측 동작 (가이드 문구와 정확히 같지는 않음)** :
  - 설정한 두 클래스 자체는 **둘 다 td 에 붙어 CSS 가 모두 적용**된다(분홍 배경 + 빨간 테두리 동시 표시). 즉 "설정할 수 없다"가 차단/무시로 구현되어 있지는 않다.
  - 다만 파생 클래스는 `{전체값}_data` 형태로 단순 문자열 결합되어 `oddClass labelClass_data` 가 되고, 브라우저가 공백으로 토큰을 쪼개면서 **마지막 클래스에만 `_data`/`_rowNumber`/`_rowStatus` 접미사가 붙는** 형태로 깨진다(`oddClass | labelClass | oddClass | labelClass_data`). 첫 클래스(`oddClass`)에 대한 파생 클래스는 생성되지 않는다.
  - 또한 footer tbody id 에 공백이 포함된 `mf_target1_oddClass labelClass_tbody` 가 생성된다.
  - → 가이드의 "공백으로 두 개 이상의 클래스를 설정할 수 없습니다"는 **사용 금지 안내**로 이해되며, 실제 엔진은 검증/차단 없이 그대로 결합하여 파생 클래스 체계가 깨지는 방식으로 동작한다. 가이드 문구는 원문 유지.

**검증 수단 (핵심)**

xlsx 파일로는 판정 불가 — 서버가 표시 문자열을 숫자로 재파싱(`"8,002.30"` -> `<v>8002.3</v>`)하고 Footer Column 의 `displayFormat` 을 numFmt 으로 그대로 적용하므로 셀 값이 달라도 화면상 동일하게 보인다(`useDataFormat`/`useStyle` 이 false 여도 numFmt 은 적용됨). 또한 Studio 미리보기 포트에서 `fetch` 로 `xmlToExcel2.wq` 를 직접 POST 하면 `<Exception><errorCode>D999` 가 발생한다.
-> `gridView_M_advancedExcelDownload_2.xml` 의 `hookRequest` 패턴으로 **메소드 호출 구간에만** `HTMLFormElement.prototype.submit` / `XMLHttpRequest.prototype.send` 를 감싸 `input[name=xmlValue]` 전송 XML 을 캡처하고 즉시 원복(실제 다운로드는 그대로 진행). 전송 XML 에서 excelCellType 이 실리는 위치를 파싱해 판정.

**전송 XML 에서 확인한 excelCellType 관련 키 (실측)**

- excelCellType 은 **전용 hashkey 가 없다.** `<data hashkey='style'>` 안에 직렬화된 GridView XML 전체가 실리고, 그 안의 `<w2:footer excelCellType="...">` 및 Footer `<w2:column excelCellType="...">` **속성 원문**으로 전달된다.
- `hashkey='footer_data'` 는 `<array><![CDATA[["8002.3","8002.3","8002.3","8002.3"]]]></array>` 로 **값만** 담고 타입 정보는 없다.
- `hashkey='useDataFormat' value='true|false'` 로 별도 전달된다(옵션 생략 시 엔진이 `"false"` 로 채워 전송 — `gridViewApiController.js:4658` `var useDataFormat = options.useDataFormat || "false";`).
- 전송 본문 내 `excelCellType` 문자열 출현 5회(= footer 1 + footer column 4). (6번째 매치는 fileName `footer_excelCellType`)

**enum 4값별 실측 전송값**

| con_excelCellType | 전송 XML `<w2:footer>` | 가이드상 Excel 표시 형식 |
|---|---|---|
| text | `excelCellType="text"` | 텍스트 |
| number | `excelCellType="number"` | 숫자 |
| bigDecimal | `excelCellType="bigDecimal"` | 숫자 |
| date | `excelCellType="date"` | 날짜 |
| (미설정) | 속성 자체가 직렬화되지 않음 | - |

- **number 와 bigDecimal 은 전송값이 서로 다르다**(`number` / `bigDecimal` 원문 그대로). 가이드상 둘 다 Excel 에서 "숫자" 로 출력되지만, 클라이언트는 값을 변환하지 않고 문자열 그대로 보내며 "숫자" 로의 수렴은 서버 렌더 단계의 처리다.
- 클라이언트에서 변환이 일어나는 값은 `definedFormat` 뿐이다(`gridViewApiController.js:4998~5000` : `excelCellType == "definedFormat"` 이면 `definedFormat{index}` 로 치환). 4개 enum 값은 어떤 변환도 거치지 않는다.

**footer vs footer column 대비 결과**

| footer excelCellType | footer column excelCellType | 전송 XML footer | 전송 XML footer column |
|---|---|---|---|
| text | date | text | date |
| number | date | number | date |

**가이드 대조 판정 (신중)**

- 본 샘플의 대상 API 인 **`footer.width` 는 결함 아님**. 가이드가 "속성값은 참고용" 이라고 명시했고, 실측도 선언값이 전혀 반영되지 않음으로 일치한다.
- `@propval` 하위절 "Footer 영역의 너비는 Footer Column 으로 결정됩니다" 는 **해석에 따라 갈린다.**
  - 해석 A ("렌더된 Footer Column 들의 폭 합") → **일치**. Footer 영역 `style.width`(559px) = 렌더된 Footer Column 폭 합(139+140+140+140) 로 항상 성립.
  - 해석 B ("`w2:footer > w2:column` 에 선언한 width") → **불일치**. B/F/G 케이스에서 선언값이 전혀 반영되지 않는다.
- 따라서 **`footer.width` 의 결함이 아니라, 별개 API 인 footer 하위 `w2:column` 의 `width` 속성이 무시되는 것이 결함 후보**다. 함께 gBody column `width` 도 무시된다(G).
- 결함 후보 대상 : `WebSquare.uiplugin.gridView.footer` / `gBody` 하위 `column` 의 `width` 속성. 가이드에 "header column width 만 유효하다" 는 서술이 있는지 별도 확인 후 Bug / Spec 판정 필요. `fail_` 샘플은 미작성(지시에 따름).

- 측정 시 `offsetWidth`(560) 는 table border 1px 을 포함하므로 컬럼 폭 합(559)과 1px 차이가 난다. 판정은 border 를 포함하지 않는 `style.width`(559px) 기준으로 수행한다.
