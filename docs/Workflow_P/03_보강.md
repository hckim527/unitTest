### 엔진 소스 근거

- `engine/Parser.js` `parseWorkflow()` 가 `<w2:workflow>` 에서 읽는 속성은 `id`, `resolveCallback`, `rejectCallback`, `processMsg` 와 하위 `<w2:step>` 배열뿐이며 `description` 은 읽지 않는다.
- `engine/Model.js` `Model.Workflow` 생성자도 `description` 을 인자로 받지 않는다.
- `engine/ModelUtil.js` `createWorkflow()` 가 복사하는 속성은 `id`, `processMsg`, `resolveCallback`, `rejectCallback`, `step`, `userData1`, `userData2`, `scope_id` 뿐이다.

### 오류 유발 경로 선택 근거

`@spec` 의 "중도 거부나 예외 없이 이행된 경우에만" 을 입증하려면 resolveCallback 이 **호출되지 않는** 경로가 필요하다. 후보 중 **Workflow 객체의 `reject()` 메소드**를 선택했다.

- 선택: `wf_reject` 의 `type="function"` step 에서 `wObj.reject("중도 거부")` 호출 → 그 **다음 step 부터** 엔진이 `promiseStatus === "REJECT"` 를 감지해 `Promise.reject` 로 전환 (`engine/ModelUtil.js` `connectFunction`/`connectPre`/`executeCallback`).
- 사유: ① 외부 네트워크 의존 없음(로컬 더미 submission 만 사용) ② 결정적으로 재현 ③ 엔진이 공식 제공하는 Workflow 객체 own 메소드(`reject`) 이므로 우회 트릭이 아님 ④ Promise chain 내부에서 처리되어 **콘솔 오류 0 건** 유지.
- 배제: 존재하지 않는 경로의 submission → 404/오류 응답 처리 경로가 서버·config 설정(errorHandler) 에 따라 달라져 로컬 재현이 불안정. `function` step 내 의도적 throw → 동작은 하나 콘솔·스택 로그가 섞여 판독을 흐림.

### 중요 — reject 는 마지막 step 에서 호출하면 무효

`ModelUtil.executeWorkflow` 의 최종 `Promise.all(promise).then(...)` 은 `promiseStatus` 를 **재검사하지 않고** 무조건 `promiseStatus = "RESOLVE"` 로 덮은 뒤 resolveCallback 을 호출한다. 즉 **마지막 step 에서 `wObj.reject()` 를 호출하면 거부가 무시되고 resolveCallback 이 그대로 실행**된다. 따라서 `wf_reject` 는 `reject` 호출 step 뒤에 후속 step(`scwin.wf_step_after`) 을 1 개 더 두어 거부가 실제로 전파되도록 구성했다.

```
[전달 파라미터] 콜백 파라미터 타입 : object / 파라미터의 id : mf_wf_ok / 실행한 Workflow 의 id : mf_wf_ok

```
